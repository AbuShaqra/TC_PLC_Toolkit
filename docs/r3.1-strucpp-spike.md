Research spike, 2026-11-09. Measured on this machine. No toolkit code was changed. Scratch inputs, scripts and
logs stay in the session scratchpad, outside the repo.

### CLI facts

- Several inputs: `strucpp a.st b.st … -o out.cpp`. The first file is the primary input and the rest are
  `additionalSources`. All of them are one project, so types resolve across files.
- **No check-only mode in the CLI.** No flag stops after semantic analysis. On success the CLI writes
  `out.cpp`/`out.hpp`; on failure it writes nothing and exits 1. `g++` runs only with `--build`.
- **Compile mode stops at the first failing pass.** Any parse error in any file means no semantic
  analysis at all (`runPipeline`, `src/index.ts` ~l.502, `if (!continueOnError && errors.length > 0) return`).
  A file with a parse error is also dropped from the project (`src/index.ts` l.474-478). So a check command
  built on the CLI shows only the first layer of errors.
- The library function `analyze()` (`src/index.ts:932`) is the check-only path. It runs with
  `continueOnError`, reports parse **and** semantic errors in one pass, and adds `pouName` / `section`
  (`body`…) / `bodyLine` to each diagnostic. The bundle cannot reach it: `scripts/bundle.mjs` bundles only
  `dist/node/cli.js`, exports nothing, and runs `main()` when loaded.
- **Wrapper proof (scratch only).** A 25-line `check.mjs` imports `analyze`, `nodeDialectIO` and
  `discoverStlibs` from the fork's `dist/node/index.js`, and esbuild bundles it into a standalone 855 KB
  `.cjs` that needs no `node_modules`. Run as its own `node` process, it prints JSON diagnostics and writes no
  files: 40 errors on the raw sample in 57–87 ms of analysis (both passes; listed below).
- Diagnostic format (CLI, stderr): `file:line:col: error: message [code]`, gcc-style. The line is 1-based,
  the column is 1-based, and the file is the input's **basename**, so two inputs with the same basename would
  be confused. A source excerpt with a caret follows. There is no JSON option. Warnings are printed only on
  success.
- **Lexer errors report `0:0`.** Chevrotain lexing errors carry `line`/`column`, but the pipeline reads
  `err.token?.startLine ?? 0` (`src/index.ts:377`, `:468`, `:972`). The message keeps an `offset` (for example
  `at offset: 288`), and the offset is correct within that file, so the caller can recover the line. This is a
  small bug in the fork.

## What the compiler rejects

### Method

1. Ran the raw and export units as they are. Every one of the 27 (raw) and 26 (export) errors is a
   **parse/lex** error, so the dialect has no effect yet (twincat3 = iec = default).
2. A scratch generator (`gen2.js`) rebuilt the raw units with minimal workarounds P1–P10. Each was added
   only after the previous run exposed the next layer. Each construct was then confirmed with a 3–10-line
   repro through the CLI and by reading the parser.
3. With all ten workarounds, the project **compiles cleanly under twincat3**. Under `iec` it gives 6 errors.
   The same holds for export mode (methods moved before the body, same text workarounds): twincat3 0 errors,
   iec 5 errors (`POINTER TO`, because export rewrites `REFERENCE TO`).

One caution about the workaround layer: P7 and P8 **comment out** five calls and two `REF=` statements, so
those lines' semantics were not checked by the compiler. While the workarounds were being built, a first
P9 regex corrupted the `E_StationState` enum and produced a bogus "CASE selector must be an integer" error.
That error was discarded and re-run; it is not a compiler finding.

**Counts.** Raw: 27 = 6 + 6 + 2 + 10 + 1 + 1 + 1 errors, from **16 root-cause sites in 7 constructs**.
Export: 26, the same minus row 6. Behind those, the next layers add rows 8–10. In total, **10 constructs**
stand between the sample and a clean compile. One is converter-only (row 1). Nine are compiler gaps, four of
which (rows 2, 5, 9, 10) a line- and column-preserving converter rewrite can paper over.

**No (d) items.** The sample uses no Beckhoff library symbols, so nothing is a missing-library error.
A real project would add a whole group here: STruC++ knows no `Tc2_*` library. The fork's bundled libs
cover IEC FBs (`TON`, `R_TRIG`, …) and functions (`LIMIT`, `*_TO_*`). Repro `ton.st` passes with `libs/`
and fails without it.

**What the profile buys.** Once past the parser, twincat3 versus iec is exactly the 6 `REFERENCE TO`/`REF=`
refusals (raw) or the 5 `POINTER TO` refusals (export). `program_methods` is not exercised by the sample,
because it has no METHOD on a PROGRAM. A repro (`prog_method.st`) passes under twincat3 and is refused under
iec. `pointer_to` matters only for export input.

**What already works (no error once reached):** FB `EXTENDS`/`IMPLEMENTS`, interface `EXTENDS` lists,
FB properties with GET/SET, ACTIONs after the body, `SUPER^.Cyclic()`, `REFERENCE TO` with `REF=` on a plain
variable, CASE over enum constants, `STRING(31)` type alias, struct and array fields, named-argument function
calls, `LREAL_TO_INT`.

### Export mode is the wrong input for a check

- Its line numbers do not match the panes.
- It **changes meaning**: `REFERENCE TO` → `POINTER TO`, `REF=` → `:=`, and FB init arguments and access
  specifiers are stripped.
- The compiler then accepts the rewritten code silently. Repro `ptr_lenient.st`: `p := g` (an FB instance
  assigned to a `POINTER TO FB_A`), `p.b` and `p.M()` with no `^` all pass, while a STRING→INT assignment is
  caught. So a check on export output would hide real errors.

R3.2 should feed the compiler a raw-based unit.

## Mapping errors to panes (input for R3.2)

A scratch script read the real raw-mode compiler output, took each `file:line:col`, and found the
`lineMap` range from the same `convertXmlToSt(…, { raw: true })` call. It mapped 21 of the 27 errors to a
component and pane. The 6 it could not map are the `0:0` lexer errors. Three were checked by hand:

| Compiler says | Maps to | Check |
| --- | --- | --- |
| `MAIN.st:16:29` | `POUs/MAIN.TcPOU`, POU MAIN, **impl** pane line 3 | Impl starts at unit line 14. Line 3 is `GVL_System.fbCylinder.Cyclic();`. Column 29 is its `(` (28 characters before it). Correct. |
| `U_Word.st:11:1` | `DUTs/U_Word.TcDUT`, **decl** line 6 | The decl is `TYPE`, `UNION`, two fields, `END_UNION`, then `END_TYPE` on line 6. Correct. |
| `FB_Cylinder.st:22:1` | `FB_Cylinder.TcPOU`, Method **FB_init**, decl line 1 | Correct. |

The `0:0` lexer errors can be recovered from their offsets: offset 288 in `GVL_Hmi.st` is the `{` on unit
line 6, which is decl line 1.

**Result: mapping works.** In raw mode the pane text is verbatim and columns are 1-based, so a column maps
1:1. These caveats apply to R3.2:

1. Some lines exist only in the generated unit: `END_METHOD`, `ACTION x`, `GET`/`SET`, `END_*`. These fall
   inside or between ranges, so errors on them (for example "Expected `END_FUNCTION_BLOCK`") need a fallback,
   such as the owning component's decl line 1.
2. The check emitter must record its own `lineMap`. It cannot reuse the live-path one once members are
   reordered (row 1) or lines are added (row 6).
3. Lexer errors need offset→line until the fork is fixed.
4. Inputs need unique file names, because diagnostics carry basenames.
5. With `analyze()` there is a cross-check: errors carry `pouName` + `section`. For example
   `MAIN.st:16:1 MAIN body …`.

## Packaging facts (input for R3.3)

- `dist/strucpp-bundle.cjs` is **1,235,797 bytes** (244 KB gzipped). It runs **standalone**: copied alone to
  an empty directory and run from `/`, `--help`, `--version` and `--print-dialect` work, with no
  `node_modules`. It bundles chevrotain 11.0.3 (Apache-2.0) and lodash-es 4.17.21 (MIT). The bundle keeps
  only lodash's licence comment.
- **`libs/` at runtime:** the bundle looks for `libs/` next to itself or one or two directories up
  (`findBundledLibsDir`, `src/node/build-utils.ts:129-160`). Without it, the sample still compiles, but any
  standard FB is "Undefined type 'TON'". These two files are enough for IEC FBs and functions (verified):
  `iec-standard-fb.stlib` (52 KB) and `iec-std-functions.stlib` (28 KB). The full `libs/` is 3.3 MB, of which
  `oscat-basic.stlib` is 1.7 MB and carries its own `LICENSE-OSCAT.txt`. Leaving out oscat, softmotion and
  `additional-function-blocks` keeps the payload around 1.3 MB and the licences simple. The `.stlib` files are
  build outputs (`npm run build`), and git ignores them.
- **Licence files to ship:** the fork's `LICENSE` and `COPYING` (GPL-3.0), `COPYING.RUNTIME` (the runtime
  library exception), a link to the source at the exact commit, and the third-party notices for chevrotain
  (Apache-2.0 `LICENSE.txt`) and lodash-es (MIT `LICENSE`). The bundle file has no GPL header of its own.
- **Node:** the fork declares `engines.node >=22.0.0`. The bundle target is `node22`.
- **Check-only**, two ways:
  - (i) **in the fork:** a `--check` flag (and ideally `--json` for diagnostics) that calls `analyze()` and
    writes nothing. This is small, but it is a change in the fork, and the fork's process rules apply to it.
  - (ii) **in the toolkit:** a tiny entry script calling `analyze()`, bundled with esbuild into its own
    `.cjs` and run as a separate process. This is proven in the spike, and it respects the no-`require()`
    licence decision.

  Option (ii) adds a toolkit-side build artefact that has to be regenerated with each fork update. Option (i)
  is cleaner. Without either, the check falls back to the CLI: it writes C++ into a temp directory, and only
  the first failing pass is visible.

## Sizing recommendation

**R3.2 (planned 5 d): 5 d holds only for a narrower scope. The full scope is 6–7 d.** The check command
itself (spawn, parse diagnostics, map to the Problems view and pane markers) fits the plan. Not planned:

1. **A line-preserving "check" emitter in `stConverter.js`, raw-based.**
   - Write members before the body (row 1).
   - Blank pragmas (row 2).
   - Rewrite the postfix enum base (row 5).
   - Optionally blank the `GVL_x.` prefix and FB init arguments (rows 10 and 9).
   - Record its own `lineMap`, with a fallback for generated lines.
   - Roughly 1.5–2 d with tests. Each rewrite must keep lines and columns.
2. **Check-only plumbing.** Either a `--check --json` in the fork, or the toolkit wrapper bundle. About 0.5–1 d.
3. **A product decision on false positives.** Even with item 1 in place, the sample still gets compiler
   errors from rows 3, 4, 6, 7 and 8: the 5 nested calls, 2 interface properties, the struct EXTENDS, the
   UNION and the `THIS^` lines. Under this project's rule, every diagnostic on `sample/` is a bug. R3.2 must
   either suppress those diagnostics, label them clearly as compiler-limitation messages that are separate
   from the toolkit's own diagnostics, or wait for the fork. This should be decided before R3.2 starts.

**R3.3 (planned 3 d): holds.** The bundle is self-contained. Add copying two `.stlib` files, the licence and
notice set above, Node ≥ 22 discovery, the settings, and the docs. If option (ii) is chosen, add about 0.5 d
for the wrapper build script.

**Out of scope for R3.2/R3.3: a fork-side track.** Rows 2–10 are compiler gaps in `AbuShaqra/STruCpp`:
- interface properties
- `a.b.M()` member-chain calls
- `THIS^.member` and `REF=` on members
- unknown-pragma skipping
- postfix enum base
- struct `EXTENDS`
- `UNION`
- FB init arguments with `FB_init`
- named and `qualified_only` GVLs
- lexer error positions
- `--check` / `--json`

Each needs parser plus semantic plus codegen work, with tests under that repo's rules. As a rough guess,
not a measurement, that is 8–12 d. Real customer projects would add Beckhoff library symbols (`Tc2_*`),
which STruC++ cannot resolve. That is a separate, larger question; the sample cannot measure it, because it
names no Beckhoff symbols. I suggest a new roadmap item for the fork-side gaps, and making R3.2's
false-positive policy explicit.

## Not determined

- **The semantics of lines the workarounds commented out:** P7 (5 member-chain calls) and P8 (2 `THIS^ REF=`).
  The compiler never checked them.
- **Behaviour on a real customer project.** Only `sample/` was run: 450 lines and no libraries.
- **Whether `analyze()` misses any error that only `compile()` raises.** The codegen phase appears to produce
  only warnings, but this was not verified exhaustively.
- **Windows behaviour** (paths, Node discovery). Not run here.
