STruC++ spike: the sample project through the compiler under the TwinCAT dialect
2 d → ~15 minNov 9

Goal of R3 overall

Check a TwinCAT project from the extension with the IEC 61131-3 compiler STruC++ (the AbuShaqra/STruCpp fork) under the TwinCAT dialect, and show its errors in the editor panes. R3 runs in three phases: this spike, the check command (#4) and packaging (#5).

Spike findings, Nov 9 · decided

The sample, as converted, gives 27 parse errors. Ten constructs stand in the way: one is ours (methods emitted after the POU body), nine are compiler gaps. With scratch workarounds it compiles with 0 errors under the TwinCAT profile and 6 under plain IEC, exactly the profile's REFERENCE TO and REF=. Errors map back to the right pane. Decided Nov 9: wait for the fork (fork lane item S2) and give the check command its full scope (7 days). Details: docs/r3.1-strucpp-spike.md.

This phase

Run the sample project through the STruC++ CLI with the TwinCAT dialect profile and list every construct it rejects. That list sizes the check command and packaging.

What exists

  • The fork (v0.7.0) loads dialect profiles with --dialect-file; features today: program_methods, pointer_to, reference_to, ref_assign.
  • The profile is in the repository as resources/dialects/twincat3.json: it builds on plain IEC and turns on all four features.
  • The toolkit already turns TwinCAT XML into one ST unit per object, with a line map back to each pane.

Constraints

  • Licence. STruC++ is GPL-3.0-only; this extension is AGPL-3.0-or-later (since PR #31). The compiler always runs as a separate process, never loaded into the extension, and ships with its licence and a source link.
  • Runtime. STruC++ needs Node 22 or later.
  • Offline. Nothing is downloaded at run time.

Decisions, settled Nov 9

  1. Output: check only. Errors in the panes, no files written, no g++ needed. Generated C++ or a built program can come later as a new item.
  2. Compiler: bundled in the extension as a single-file build.
  3. Node 22: found on the user's machine (PATH or a setting), with a clear message when it is missing. VS Code 1.66 support stays.

#12R12Done · Nov 12›
Language server: {IF}-aware diagnostics
1 d → ~45 minNov 12

Goal

The language server's diagnostics stop flagging valid code inside {IF} / {ELSIF} / {ELSE} / {END_IF} groups (a different block head per branch, a type that differs per branch, a name declared only in a branch) without losing diagnostics on code outside groups. The sample/ diagnostics gate stays at zero.

Decided Nov 11 (your call)

Scheduled by the user to follow PR #35 (merged Nov 11 23:55 UTC); started Nov 11 23:57 UTC.

Design

The language server never evaluates a define: every branch combination counts. A block error is kept only when every branch selection has it (at most 64 selections per method or body; a segment with broken directives reports nothing). Other diagnostics inside a group's statement are dropped. A name whose type differs per branch resolves to unknown. Code with no {IF} gets exactly the old output.

Built Nov 11–12, PR #36

Built Nov 11 23:57 to Nov 12 00:39 UTC on claude/focused-ptolemy-m6acaz, review findings fixed, pushed and open as PR #36 into dev. The review round (a named argument such as SET := on its own line no longer splits a method, enum members inside a group are kept, a nested group no longer hides the next statement, a wrapped first VAR block keeps the undeclared check). New src/lsp/conditionals.js and test/test_conditional_pragmas.js, live-path cases, and a compiler-parity check (a fixture the compiler accepts under some define set must get 0 diagnostics). 111/111 suites FULL, lint and typecheck clean, dev host 103/1 (the known P8 line-ending failure).
