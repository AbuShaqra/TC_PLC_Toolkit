R1

Generate ST button: rounded end in single-project workspaces

Order 1 · 0.5 d · Nov 10

Problem

Generate ST is a split button: the main button plus a caret that opens the project picker. The caret appears only when the workspace has two or more PLC projects. With one project it is hidden, but the main button keeps its squared right corners, so it looks cut off.

Cause

media/editor.css:413-416 squares the main button's right corners in every case. The caret starts hidden (src/customEditorProvider.js:559) and media/editor.js shows it only for two or more projects.

Plan

Square the corners only while the caret is visible: the webview toggles a class on the button group together with the caret, and the CSS keys on that class. CSS :has() is not an option, because the oldest supported VS Code (1.66) ships a Chromium that predates it.

Done when

Both states look right in the dev host, and both browser harnesses pass.

R4

Objects-tree model (deepening roadmap P7)

Order 3 · 4 d · Nov 13–18

Goal

Give the TwinCAT Objects view a real node model with no VS Code dependency, so the tree provider becomes a thin adapter. This is the last open phase of the deepening roadmap.

Plan

A new src/objectsTreeModel.js holds the node graph: parent links, children and stable ids. It also takes over the "fewer than two projects means a flat tree" rule, which today sits in the LSP's project-ownership module (src/lsp/projectMap.js:297). The tree provider then reads parents and children straight from the model, and the reveal test no longer needs a vscode stub.

Done when

Finding a node's parent needs no scan and builds no sibling nodes; each node's id and menu context are set in one place; the suite and typecheck pass; and the live dev-host test passes on your Windows machine. That last test is mandatory, because reveal and tab identity are exactly what this changes, and only the live test caught the 0.6.0 duplicate-tab bug in this area.

R2

Create a new TwinCAT project from the extension

Order 4 · 5 d · Nov 19–25 · Decisions open

Goal

A user with no TwinCAT project in the workspace, or an empty folder, creates one from the extension's start view without opening TwinCAT XAE first.

Start view

The TwinCAT Objects view has no empty-state content today. It gets a Create TwinCAT Project button bound to a new command, also available from the Command Palette.

Key constraint

A TwinCAT solution chains .sln → .tsproj → .plcproj. Only XAE has ever written a skeleton XAE accepts: hand-written ones were refused, and the on-disk template is a 67-byte stub XAE expands when it inserts a project. Two routes:

  • Template from an XAE-made skeleton. Ship a skeleton XAE produced, then copy it, rename it and regenerate every identity GUID. Offline, any OS, no TwinCAT needed. Must be proven to open and build in XAE first.
  • Drive XAE. Automate XAE the way the sample-project script already does. Always valid, but Windows-only and needs TwinCAT installed.

Decisions open

  1. Template, XAE automation, or the template with XAE automation where TwinCAT is present.
  2. A full solution only, or also a PLC project added to an existing solution.
  3. Which TwinCAT version the template targets.
  4. Starter content: an empty MAIN, a task, a GVL.
R3

Compile TwinCAT projects with STruC++

Orders 2, 5, 6 · 10 d · Decisions open

Goal

Compile a TwinCAT project from the extension with the IEC 61131-3 compiler STruC++ (the AbuShaqra/STruCpp fork), under the TwinCAT dialect, and show its errors in the editor panes.

What exists

  • The fork (v0.7.0) loads dialect profiles: JSON files selected with --dialect, --dialect-file or --dialect-path. Profile features today: program_methods, pointer_to, reference_to, ref_assign.
  • The TwinCAT profile, twincat3.json, is vendored from Lemvane as a single file. It is the only thing taken from Lemvane, which stays read-only to this project.
  • The toolkit already turns TwinCAT XML into one ST unit per object, with a line map back to each pane. That is the compiler's input and the route for mapping its errors back.

Constraints

  • Licence. STruC++ is GPL-3.0-only, with a runtime-library exception for compiled programs; the extension is MIT. The compiler stays a separate program the extension runs as a process, never loaded into the extension, and any bundled copy ships with its licence and a source reference.
  • Runtime. STruC++ needs Node 22 or later; the extension supports VS Code 1.66 and later, whose bundled Node is older.
  • Offline. The extension works offline, so a bundled compiler fits better than a download on first use.
  • Binaries. Building the generated C++ into a program needs g++; checking and generating C++ does not.

Phases

  1. R3.1 Spike (2 d, Nov 11–12). Vendor twincat3.json, run the sample project through the STruC++ CLI under the TwinCAT dialect, and list every construct it rejects. This sizes the rest.
  2. R3.2 Compile command (5 d, Nov 26 – Dec 2). Convert the project, run the compiler, and map errors to the right component and pane.
  3. R3.3 Packaging (3 d, Dec 3–7). Bundle or locate the compiler, ship the licence files, add settings and documentation.

Decisions open

  1. What compiling produces: checking only, generated C++, or a built program.
  2. Bundle the compiler in the extension, or use one the user installs.
  3. How to supply Node 22: raise the minimum VS Code version, or find a Node on the user's machine.

Backlog, not scheduled

Carried from the project's handoff notes. Each waits for a recorded reason.

  • Indexing speed: cache signature-file discovery per root; per-project background scan; persistent archive cache.
  • Rename: keep .plcproj updates inside the rename transaction; rename sibling implementors of an interface.
  • Reverse index for Find References, only past about 1000 files or 200 ms.
  • Tooling: ESLint 10; a development-only dependency advisory.
  • Language: nested block comments; hover help for pragmas.
