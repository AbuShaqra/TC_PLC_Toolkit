#1R1Planned›
Generate ST button keeps its rounded end in single-project workspaces
0.5 dNov 10

Problem

Generate ST is a split button: the main button plus a caret that opens the project picker. The caret appears only with two or more PLC projects. With one project it is hidden, but the main button keeps its squared right corners, so it looks cut off.

Cause

media/editor.css:413-416 squares the main button's right corners in every case. The caret starts hidden (src/customEditorProvider.js:559) and media/editor.js shows it only for two or more projects.

Plan

Square the corners only while the caret is visible: the webview toggles a class on the button group together with the caret, and the CSS keys on that class. CSS :has() is not an option: VS Code 1.66 ships a Chromium that predates it.

Done when

Both states look right in the dev host, and both browser harnesses pass.

#2R3.1Planned›
STruC++ spike: the sample project through the compiler under the TwinCAT dialect
2 dNov 11 – 12

Goal of R3 overall

Check a TwinCAT project from the extension with the IEC 61131-3 compiler STruC++ (the AbuShaqra/STruCpp fork) under the TwinCAT dialect, and show its errors in the editor panes. R3 runs in three phases: this spike, the check command (#5) and packaging (#6).

This phase

Run the sample project through the STruC++ CLI with the TwinCAT dialect profile and list every construct it rejects. That list sizes the check command and packaging.

What exists

  • The fork (v0.7.0) loads dialect profiles with --dialect-file; features today: program_methods, pointer_to, reference_to, ref_assign.
  • The profile is in the repository as resources/dialects/twincat3.json: it builds on plain IEC and turns on all four features.
  • The toolkit already turns TwinCAT XML into one ST unit per object, with a line map back to each pane.

Constraints

  • Licence. STruC++ is GPL-3.0-only; the extension is MIT. The compiler always runs as a separate process, never loaded into the extension, and ships with its licence and a source link.
  • Runtime. STruC++ needs Node 22 or later.
  • Offline. Nothing is downloaded at run time.

Decisions, settled Nov 9

  1. Output: check only. Errors in the panes, no files written, no g++ needed. Generated C++ or a built program can come later as a new item.
  2. Compiler: bundled in the extension as a single-file build.
  3. Node 22: found on the user's machine (PATH or a setting), with a clear message when it is missing. VS Code 1.66 support stays.
#3R4Needs Windows›
Objects-tree model (deepening roadmap P7)
4 dNov 13 – 18

Goal

Give the TwinCAT Objects view a real node model with no VS Code dependency, so the tree provider becomes a thin adapter. The last open phase of the deepening roadmap.

Plan

A new src/objectsTreeModel.js holds the node graph: parent links, children and stable ids. It takes over the "fewer than two projects means a flat tree" rule from the LSP's project-ownership module (src/lsp/projectMap.js:297). The provider reads parents and children straight from the model, and the reveal test no longer needs a vscode stub.

Done when

Finding a node's parent needs no scan and builds no sibling nodes; each node's id and menu context are set in one place; the suite and typecheck pass; and the live dev-host test passes on your Windows machine. That test is mandatory: reveal and tab identity are exactly what this changes, and only the live test caught the 0.6.0 duplicate-tab bug in this area.

#4R2Needs Windows›
Create a new TwinCAT project from the extension's start view
6 dNov 19 – 26

Goal

A user with no TwinCAT project in the workspace, or an empty folder, creates one from the extension without opening TwinCAT XAE first.

Start view

The TwinCAT Objects view has no empty-state content today. It gets a Create TwinCAT Project button bound to a new command, also in the Command Palette.

Key constraint

A TwinCAT solution chains .sln → .tsproj → .plcproj, and only XAE has ever written a skeleton XAE accepts: hand-written ones were refused. So the templates are skeletons XAE produced, copied with every identity GUID regenerated.

Decisions, settled Nov 9

  1. Approach: the template, with XAE automation offered as well where TwinCAT is installed.
  2. Scope: a new solution only, in an empty or project-less folder.
  3. TwinCAT version: both 3.1.4026 and 3.1.4024, the user picks. The 4026 skeleton already exists; the 4024 one must be made by a 4024 XAE on your machine. Each is proven to open and build in its own XAE.
  4. Starter content: PROGRAM MAIN, the PlcTask that calls it, and an empty GVL.

About›
Why this order
  1. R1 first. Half a day, confined to the webview, and it fixes a visible defect now.
  2. The STruC++ spike next. The compiler work is the largest unknown, and the spike sizes the rest of R3 while other work goes on.
  3. R4 before R2. R2 adds an empty state and a create flow to the Objects tree, and R4 rebuilds that tree's model. Doing R4 first means R2 is written once.
  4. R2, then the rest of R3. R2 needs its templates made and proven in XAE on your machine, the same session R4's live test needs. The rest of R3 builds on the spike.
