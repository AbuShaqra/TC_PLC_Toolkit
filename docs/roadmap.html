#1R3.1Findings done›
STruC++ spike: the sample project through the compiler under the TwinCAT dialect
2 d → ~15 minNov 9

Goal of R3 overall

Check a TwinCAT project from the extension with the IEC 61131-3 compiler STruC++ (the AbuShaqra/STruCpp fork) under the TwinCAT dialect, and show its errors in the editor panes. R3 runs in three phases: this spike, the check command (#4) and packaging (#5).

Spike findings, Nov 9 · decided

The sample, as converted, gives 27 parse errors. Ten constructs stand in the way: one is ours (methods emitted after the POU body), nine are compiler gaps. With scratch workarounds it compiles with 0 errors under the TwinCAT profile and 6 under plain IEC, exactly the profile's REFERENCE TO and REF=. Errors map back to the right pane. Decided Nov 9: wait for the fork (fork lane item S2) and give the check command its full scope (7 days). Details: docs/r3.1-strucpp-spike.md.

This phase

Run the sample project through the STruC++ CLI with the TwinCAT dialect profile and list every construct it rejects. That list sizes the check command and packaging.

What exists

  • The fork (v0.7.0) loads dialect profiles with --dialect-file; features today: program_methods, pointer_to, reference_to, ref_assign.
  • The profile is in the repository as resources/dialects/twincat3.json: it builds on plain IEC and turns on all four features.
  • The toolkit already turns TwinCAT XML into one ST unit per object, with a line map back to each pane.

Constraints

  • Licence. STruC++ is GPL-3.0-only; the extension is MIT. The compiler always runs as a separate process, never loaded into the extension, and ships with its licence and a source link.
  • Runtime. STruC++ needs Node 22 or later.
  • Offline. Nothing is downloaded at run time.

Decisions, settled Nov 9

  1. Output: check only. Errors in the panes, no files written, no g++ needed. Generated C++ or a built program can come later as a new item.
  2. Compiler: bundled in the extension as a single-file build.
  3. Node 22: found on the user's machine (PATH or a setting), with a clear message when it is missing. VS Code 1.66 support stays.

Objects-tree model (deepening roadmap P7)
4 d → ~3 hNov 9 · merged

Goal

Give the TwinCAT Objects view a real node model with no VS Code dependency, so the tree provider becomes a thin adapter. The last open phase of the deepening roadmap.

Plan

A new src/objectsTreeModel.js holds the node graph: parent links, children and stable ids. It takes over the "fewer than two projects means a flat tree" rule from the LSP's project-ownership module (src/lsp/projectMap.js:297). The provider reads parents and children straight from the model, and the reveal test no longer needs a vscode stub.

Done when

That test is mandatory: reveal and tab identity are exactly what this changes, and only the live test caught the 0.6.0 duplicate-tab bug in this area.

#3R2Phase 1 built · XAE proofs next›
TwinCAT sidebar and start page; create a new project (4024 / 4026)
8.5 d → ~6 h + XAENov 12 – 13

Goal

The extension gets its own place in the Activity Bar, and a user with no TwinCAT project, or an empty folder, creates one there without opening TwinCAT XAE first.

Sidebar and start page, decided Nov 9 (your ask)

A TwinCAT icon in the Activity Bar opens a sidebar with a Start view plus TwinCAT Objects and TwinCAT Libraries, which move out of the Explorer (you can still drag them back). The Start view has compact buttons; Open Start Page opens a full page in an editor tab with: create a new project (3.1.4024 or 3.1.4026, name, location), open an existing project (with recent solutions), project actions (Generate ST, Update Library Definitions, and the STruC++ check once R3.2 ships), help and links, and settings. Every action is also a command. This grows R2 from 6 to about 8.5 days.

Key constraint

A TwinCAT solution chains .sln → .tsproj → .plcproj, and only XAE has ever written a skeleton XAE accepts: hand-written ones were refused. So the templates are skeletons XAE produced, copied with every identity GUID regenerated.

Decisions, settled Nov 9

  1. Approach: the template, with XAE automation offered as well where TwinCAT is installed.
  2. Scope: a new solution only, in an empty or project-less folder.
  3. TwinCAT version: both 3.1.4026 and 3.1.4024, the user picks. The 4026 skeleton already exists; the 4024 one arrived from your XAE on Nov 9 (it saves the system project as one .tspproj, where 4026 wrote .tsproj plus _Config/). Each is proven to open and build in its own XAE.
  4. Starter content: PROGRAM MAIN, the PlcTask that calls it, and an empty GVL.

Status, Nov 9

Phase 1 is built (not yet a PR): the TwinCAT sidebar, the start page, and Create New Project from templates made from the XAE skeletons, with every identity GUID regenerated. A new project has MAIN, the PlcTask and an empty GVL_Main, and shows zero diagnostics. Before merge, on your machine: create one project per version and prove it opens and builds in XAE 3.1.4024 and 3.1.4026, and run the dev-host pass. Phase 2, creating through XAE where TwinCAT is installed, is not started.

#9S9Done · Nov 10›
Raw memory layout in the runtime
4 d → ~2 hNov 11

Scope

Every runtime variable carries its forcing state next to its value, so a BYTE takes 3 bytes and memory is not laid out as on a PLC. Reading a DWORD's bytes through POINTER TO ARRAY OF BYTE, or walking an array or STRUCT with POINTER TO BYTE, reads wrong values; 14 functions of the bundled OSCAT library do this with STRINGs. After S9 a variable is just its value, a STRING is a NUL-terminated buffer, and forcing lives in a bounded table written at cycle start and end.

Steps (one PR each)

S0 library manifest lists FUNCTION locals as inputs (merged, #58) · S1 force table (merged, #59) · S2 code generation (merged, #60) · S3a debugger, REPL and editor forcing (merged, #61) · S3b the layout (merged, #62) · S4 STRING (merged, #63) · S5 OSCAT functions through real calls (merged, #64). Done. About 1,550 lines of source and 2,200 of tests.

Decided

User, Nov 10: fix the root cause; PLC-style forcing (applied at cycle start and end, a program write wins until cycle end). Mine: force table bounded at 64 + 8 strings (16 + 1 on AVR), overridable.

Design check

A prototype runtime compiled today's generated C++ unchanged and fixed every wrong-byte case and 7 OSCAT functions. Strict aliasing must be handled (an attribute, plus a build flag as backup).

Impact

Release F on its own. Users see: the forcing change, SIZEOF as on a PLC (STRING(80) = 81), a STRING ending at its first $00, a bound on forced variables.

About›
Why this order
  1. The STruC++ spike first. The compiler work is the largest unknown, and the spike sizes the rest of R3 while other work goes on.
  2. R4 before R2. R2 adds an empty state and a create flow to the Objects tree, and R4 rebuilds that tree's model. Doing R4 first means R2 is written once.
  3. The fork lane's S2 before the check command. A check that flags correct code is worse than none, so the compiler gaps are closed in the fork first (decided Nov 9).
  4. R2, then the rest of R3. R2 needs its templates made and proven in XAE on your machine, the same session R4's live test needs. The rest of R3 builds on the spike.
